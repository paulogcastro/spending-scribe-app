# Architecture
- Keep financial data in the existing browser storage for this local-only workflow; backups must include all months and merchant category preferences without introducing a hosted service.
- Centralize spending pace calculations and backup validation in pure library functions so financial rules can be tested independently of presentation.
- Use semantic color tokens and shared goal indicators across financial sections for consistent theming and budget status.
- Store cycle metadata and selected cycle in a separate versioned local key; never migrate, delete, or reinterpret legacy monthly records automatically.
- Represent cycles as local civil-date half-open intervals and centralize date navigation and storage validation in pure functions to avoid timezone shifts and overlapping boundaries.
- Until financial modules are explicitly restructured, bridge cycle selection to its start calendar month and label those records as monthly; existing finance rules, imports and copying remain monthly.
- Derive displayed monthly and cycle periods with financialPeriods; never compare cycle investment goals to monthly actuals or subtract them from monthly results, because the civil-date intervals differ.
- Store per-cycle planning (salary, extra incomes, investment base goal, budget distribution) in its own versioned local key indexed by cycleId, with all formulas centralized in pure library functions; legacy MonthlyData stays untouched.
- Keep the independent expense domain's schemas, inferred types, reference validation and storage access in expenseDomain; occurrences are indexed by cycle, with one budget group and separate nature/category/payment IDs, so legacy records remain untouched.
- Manual expense and catalog mutations stay in expenseDomain, with useExpenseDomain owning validated persistence and CycleExpenses keyed by the selected cycle; occurrence dates do not choose or restrict cycle membership, preventing accidental reassignment and mixed-cycle edits.
- Backups v3 include the independent expense domain alongside all previous data; validate before writes and rollback on failure, while v1/v2 restore only their included domains to preserve newer data.
- Keep commitment generation, schedule progress and corrections in expenseDomain; optional cycle-effective definition snapshots preserve unvisited history and backup v3 compatibility, while future projections remain unpersisted and edits start after the current cycle to protect materialized occurrences.
